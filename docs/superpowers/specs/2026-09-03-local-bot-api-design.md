# Локальный Bot API, индикация прогресса и гарантированная уборка файлов

**Дата:** 2026-09-03
**Статус:** утверждён владельцем, готов к планированию
**Базовый коммит:** `67eefba`

---

## 1. Цель

Снять потолок в 50 МБ на отправляемый файл, перейдя с облачного Bot API на
самостоятельно поднятый `telegram-bot-api`. Из этого следуют две обязательные
сопутствующие задачи:

1. **Индикация.** Загрузка и отправка гигабайтного файла занимают минуты. Без
   обратной связи бот выглядит зависшим.
2. **Уборка.** Файлы такого размера не должны оставаться на диске после отправки
   ни на одном пути выполнения, включая провалы и отмены.

Владелец расширил объём до «транспорт + структурно связанное + качество»: без
снятия пина клиентов YouTube лимит в 2 ГБ окажется бесполезным, потому что
YouTube продолжит отдавать 360p.

## 2. Измеренные ограничения хоста

Замерено 2026-09-03 на целевом хосте (RK3399, aarch64, Linux 5.18):

| Ресурс | Значение | Следствие для дизайна |
|---|---|---|
| `/` (eMMC, `mmcblk0p1`) | 15 ГБ, свободно 2.3 ГБ (83%) | загрузки сюда класть нельзя |
| `/mnt/storage` (`sda2`) | 1.6 ТБ, свободно 1.3 ТБ, запись 53.6 МБ/с | целевое место под загрузки и том сервера |

| Исходящий канал | 9.6 МБ/с (77 Мбит/с) до Cloudflare | до дата-центров Telegram по MTProto будет медленнее — требуется отдельный замер |

## 4. Архитектура

### 4.1. Транспорт

Отдельный контейнер `telegram-bot-api` (образ `aiogram/telegram-bot-api`), host-сеть,
слушает `127.0.0.1:8081`, запускается с `--local`. Бот получает сессию, указывающую
на него:

```python
session = AiohttpSession(
    api=TelegramAPIServer.from_base(settings.TELEGRAM_API_BASE, is_local=True),
    timeout=settings.TELEGRAM_REQUEST_TIMEOUT,
)
```

`TelegramAPIServer.from_base(base, is_local=True)` подтверждён в установленном
aiogram 3.30.0. Параметр `is_local` в aiogram влияет только на **скачивание**
файлов, поэтому на отдачу он не действует — её решаем отдельно.

**Отдача файла путём, а не байтами.** В aiogram 3.30.0 поле объявлено как
`SendVideo.video: str | InputFile`, то есть строка допустима на уровне типов и
уходит в форму как есть. Бот и сервер монтируют одну и ту же хостовую папку
**по одинаковому пути внутри обоих контейнеров**, и бот отправляет
`file:///srv/jw_downloads/<uuid>/<name>.mp4` вместо `FSInputFile`.

Это даёт: отсутствие перекладывания гигабайтов через HTTP, отсутствие второй копии
в `--temp-dir` и отсутствие траты RAM на форму.

Имена файлов санитизируются до `[A-Za-z0-9._-]` перед формированием URI. Текущая
схема (`uuid4().hex` + расширение) этому уже удовлетворяет, но правило
фиксируется явно, потому что имена частично формирует gallery-dl.

### 4.2. Потолок размера

Выводится из бюджета в 500 секунд, а не из лимита API:

- 1900 МБ требуют устойчивых ≥ 3.8 МБ/с;
- 1500 МБ требуют устойчивых ≥ 3.0 МБ/с.

**Стартовое значение — `MAX_FILE_SIZE_MB=1500`.** В смоук-тесте отправляется
реальный файл около 1 ГБ, замеряется фактическая скорость до Telegram, и только
по результату значение поднимается до 1900. Даже стартовое значение в 30 раз
больше нынешнего.

### 4.3. Обработка исхода отправки

`_send_with_retry` (`user.py:67-95`) переписывается:

- `TelegramEntityTooLarge` наследует `TelegramNetworkError` (проверено на aiogram
  3.30.0), поэтому сейчас оверсайз-файл переотправляется четыре раза. Он
  перехватывается **до** сетевой ветки и не ретраится.
- Гейт размера **до** отправки: файл больше `MAX_FILE_SIZE_MB` не отправляется
  вовсе, пользователь получает внятное сообщение, квота не тратится.
- Если сетевая ошибка возникла позже, чем через 400 секунд **с момента начала
  попытки отправки** (то есть близко к серверному лимиту в 500 с), она трактуется
  как «вероятно доставлено»: повтора нет, пользователю сообщается, что файл,
  скорее всего, уже в чате. Порог намеренно ниже 500 с, чтобы покрыть погрешность
  измерения и время установления соединения.
- Мелкие отправки ретраятся как раньше.

### 4.4. Индикация прогресса

Новый модуль `bot/services/progress.py`.

**`ProgressReporter`** — обёртка над статусным сообщением:

- правка не чаще, чем раз в 3 секунды, и только если отрисованный текст изменился;
- `TelegramBadRequest` с «message is not modified» — no-op, а не дубль сообщения;
- `TelegramRetryAfter` — отступ, а не исключение;
- **никогда не пробрасывает исключение наружу**: сбой индикации не должен ронять загрузку.

**Источник прогресса загрузки.** Сейчас `downloader.py:362` и `:256` используют
`process.communicate()`, который буферизует stdout до завершения процесса —
прогресс не виден в принципе. Заменяется на потоковое чтение `process.stdout`
построчно с **параллельным стоком stderr** (иначе переполнение буфера пайпа даст
дедлок), а `asyncio.wait_for` переносится с `communicate()` на весь цикл чтения.

yt-dlp получает `--newline` и `--progress-template` с сырыми числовыми полями
(`downloaded_bytes`, `total_bytes`, `total_bytes_estimate`, `speed`, `eta`, `status`),
форматирование остаётся на стороне бота. Для фазы склейки используется
`--progress-template postprocess:...`.

gallery-dl структурированного прогресса не даёт — считаем сохранённые файлы по
строкам вывода и показываем счётчик.

**Канал обратной связи.** `download_media(url, platform)` получает параметр
`progress_cb`, который протягивается в `_try_gallery_dl` и `_try_gallery_dl_fallback`.
Хендлер передаёт колбэк, замкнутый на `ProgressReporter`.

**Что видит пользователь:**

```
⏳ В очереди…                                      ← занят семафор
🔎 Анализирую ссылку…
⬇️ Скачиваю  [████████░░░░]  67%  ·  1.31/1.95 ГБ  ·  11.2 МБ/с  ·  ~52 с
🎬 Собираю видео и звук…                           ← фаза ffmpeg
📤 Отправляю в Telegram  ·  1.5 ГБ  ·  прошло 2:14  ·  осталось ≈ 2 мин
```

**Честность четвёртой фазы.** Реальный прогресс отдачи `сервер → Telegram` изнутри
бота недоступен, а измерять `бот → сервер` бессмысленно — это localhost, полоска
долетела бы до 100% за секунды и замерла, что хуже отсутствия индикации.
Стат-порт сервера для этого не используется (см. §3 — утечка токена). Поэтому
показывается счётчик прошедшего времени и оценка остатка по **скользящей средней
фактической скорости прошлых отправок**, а не по константе. До накопления
статистики оценка не показывается, только счётчик времени.

### 4.5. Жизненный цикл файлов

Гарантия делается структурной, а не дисциплинарной.

**Папка на загрузку.** Сегодня всё качается в одну плоскую директорию, изоляция —
только префикс имени, причём `uuid` создаётся внутри `download_media`
(`downloader.py:311`) и наружу не возвращается, поэтому хендлер физически не может
удалить мусор. Вводится `<DOWNLOAD_ROOT>/<uuid>/`; **директорию создаёт хендлер**
и передаёт в `download_media`. Кто создал — тот и удаляет.

**Один `finally` на обе фазы.** Сейчас `finally` (`user.py:417`) накрывает только
отправку, а провал загрузки уходит через `return` на `:273` — до `try` на `:278`,
то есть мимо уборки. `try` поднимается сразу под создание статусного сообщения;
в `finally` — один `shutil.rmtree(work_dir, ignore_errors=True)`. Это схлопывает
шесть вызовов `_cleanup_glob` (`downloader.py:332, 367, 377, 391, 436, 441`) в
одну операцию.

**Отмена.** Guard в `downloader.py:439` — `except Exception`, который не ловит
`CancelledError`. Уборка в `finally` хендлера от этого не зависит и отработает.

**Подметальщик как страховка.** `cleanup.py` переписывается:

- `stat()` переносится внутрь `try` — сейчас он снаружи (`:32` против `:33-37`), и
  одна гонка с уборкой хендлера убивает задачу навсегда и молча;
- обход становится рекурсивным по директориям (сейчас `file.is_file()` на верхнем
  уровне, то есть новые подпапки были бы полностью проигнорированы);
- `try` на каждую запись плюс внешний `try` вокруг тела цикла — цикл не может умереть;
- в `__main__.py:35` добавляется `add_done_callback` с логированием и перезапуском;
- порог возраста поднимается с 10 до 45 минут;
- ведётся **реестр активных рабочих папок** в памяти процесса: они не удаляются ни
  при каком возрасте. Сейчас подметальщик способен удалить файл прямо во время
  отдачи (порог 10 минут против худшего времени отправки ~12.6 минут).

**Предполётная проверка места.** Перед загрузкой проверяется
`shutil.disk_usage(DOWNLOAD_ROOT).free`; ниже порога — внятный отказ, а не падение
в середине процесса.

### 4.6. Качество и целостность

- **ffprobe-гейт перед отправкой.** Проверяются наличие видеопотока и аудиопотока,
  ненулевая длительность и реальные `width`/`height`; последние передаются в
  `reply_video`, чтобы Telegram не угадывал. Это ловит video-only DASH-фрагмент до
  того, как будет потрачено несколько минут на его отдачу. Для осознанно
  фотографического контента аудиопоток не требуется.
- **Белый список расширений** в `_find_downloaded_files` (`downloader.py:213-226`).
  Сейчас предикат — только `name.startswith(prefix)`, поэтому недокачанный
  `.part` и video-only фрагмент `.f137` уходят пользователю как готовое видео.
  Явно исключаются `.part`, `.ytdl`, `.f<id>`.
- **YouTube:** снимаются `--extractor-args youtube:player_client=web_safari,android_vr,tv`
  и `--compat-options manifest-filesize-approx` (`downloader.py:190-191`) — замерено,
  что из-за них отдаётся жёсткие 360p. Deno в образе уже есть для JS-челленджей.
- **Селекторы форматов** переписываются без арифметики `MAX-5`/`MAX-2`/`MAX-15`
  (`downloader.py:174, 193-197`), которая была настроена под 50 МБ. Сохраняются:
  приоритет H.264/avc1 над AV1 для Facebook (иначе «звук без картинки») и
  анти-watermark селектор для TikTok.
- **Убийство группы процессов по таймауту.** `process.kill()` (`downloader.py:365`)
  убивает только прямого потомка, осиротевший ffmpeg продолжает жить. Процесс
  запускается с `start_new_session=True`, по таймауту убивается группа.

### 4.7. Конкурентность

`download_semaphore` (`user.py:36`) сейчас равен 3 и накрывает только загрузку
(`:260-261`), освобождаясь до начала отдачи. Становится **2** и накрывает загрузку
**и** отправку. Причина: канал один, и параллельные отдачи делят его между собой —
при трёх одновременных полуторагигабайтных аплоадах каждый замедляется втрое, что
прямо повышает риск упереться в серверные 500 секунд. Два — компромисс между
пропускной способностью и этим риском.
Ожидающие видят «⏳ В очереди…», а не тишину.

## 5. Изменения конфигурации

Новые параметры в `bot/config.py`:

| `DOWNLOAD_ROOT` | `/srv/jw_downloads` | вытесняет захардкоженный `Path("/tmp/jw_downloads")`, продублированный в `downloader.py:18` и `cleanup.py:10` |
| `MIN_FREE_DISK_GB` | `5` | порог предполётной проверки |
| `CLEANUP_MAX_AGE_MIN` | `45` | порог возраста для подметальщика |

Изменяемые:

| Параметр | Было | Стало |
|---|---|---|
| `MAX_FILE_SIZE_MB` | 50 | 1500 (до 1900 после замера) |
| `DOWNLOAD_TIMEOUT` | 120 | 900 |
| `AiohttpSession(timeout=…)` (`__main__.py:22`) | 180 | из `TELEGRAM_REQUEST_TIMEOUT` |

Сообщение о таймауте (`downloader.py:368`) содержит захардкоженное «120 секунд» —
подставляется фактическое значение.

## 6. Изменения инфраструктуры

`docker-compose.yml`:

- новый сервис `telegram-bot-api`: образ `aiogram/telegram-bot-api`, `network_mode: host`,
  `restart: always`, `TELEGRAM_LOCAL=1`, api_id/api_hash из `.env`. Конкретные пути:
  рабочий каталог `/mnt/storage/jw_tg_api/data` → `/var/lib/telegram-bot-api`,
  temp-dir `/mnt/storage/jw_tg_api/temp` → `/tmp/telegram-bot-api`. Оба лежат на
  `/mnt/storage`, **не на eMMC и, что важнее, не внутри папки загрузок** — иначе
  сборщик мусора TDLib начнёт удалять наши файлы (см. §3);
- порт `8082` не публикуется, стат-порт не используется;
- healthcheck по основному порту `8081`;
- у сервиса `bot` секция `tmpfs: /tmp/jw_downloads:size=200M` **удаляется** и
  заменяется bind-монтированием `/mnt/storage/jw_downloads:/srv/jw_downloads`;
  тот же хостовый путь монтируется в контейнер сервера **по тому же пути**, иначе
  переданный по `file://` путь у сервера не разрешится;
- `secrets/` монтируется `:ro`;
- сохраняется `network_mode: host` для бота — Docker-NAT на этом хосте роняет
  аплоады крупнее ~1.5 МБ (MTU 1280 на пути до Telegram).

Том сервера содержит токен бота именем директории, поэтому исключается из
`.gitignore` и `.dockerignore` и не попадает в `/mnt/backup`.

## 7. Раннбук миграции

1. Владелец вписывает `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` в `.env`.
2. Сборка и подъём сервиса `telegram-bot-api`, проверка живости.
3. Смоук-тест на **отдельном тестовом токене** (боевой пока на облаке): все
   платформы, файл около 1 ГБ, замер фактической скорости отдачи.
4. По результату замера фиксируется итоговый `MAX_FILE_SIZE_MB`.
5. Сверка `sha256` кода в контейнере с git HEAD.
6. Только после этого — **однократный** `logOut` боевого бота на облачном Bot API
   и переключение боевого токена на локальный сервер.

Возврат на облако возможен, но требует повторного `logOut` уже с локального
сервера, что уничтожит каталог бота на нём.

## 8. Тест-план

- Загрузка и отправка файлов на 5, 50, 500 и ~1000 МБ.
- Каждая поддерживаемая платформа: YouTube, Instagram (reels и карусели), TikTok
  (видео и `/photo/` слайдшоу), Facebook, Pinterest.
- ffprobe-гейт: искусственно подсунуть video-only файл — не должен уйти как успех.
- Уборка: после каждого сценария `DOWNLOAD_ROOT` пуст. Отдельно проверить провал
  загрузки, таймаут, отмену (рестарт контейнера в середине) и ошибку отправки.
- Подметальщик: удалить файл в момент обхода, убедиться, что задача жива.
- Прогресс: правки статуса не чаще чем раз в 3 с, «message is not modified» не
  порождает дублей.
- Оверсайз: файл больше лимита не отправляется и не ретраится.

## 9. Риски

| Риск | Смягчение |
|---|---|
| Реальная скорость до Telegram ниже 3 МБ/с → упор в 500 с | стартовый лимит 1500 МБ, замер в смоук-тесте, при необходимости снижение |
| Таймаут при доставленном файле → дубль | сетевая ошибка на долгой отправке не ретраится |
| Том сервера с токеном попадёт в бэкап | явное исключение в `.gitignore`/`.dockerignore`, том вне `/mnt/backup` |
| Переполнение eMMC | всё крупное на `/mnt/storage`, предполётная проверка места |
